# Verbalization Protocol

将面向屏幕的默认回答模式切换为面向耳朵的表达模式。最终回复会直接交给普通文本转语音引擎，听众可能边走路边听，不能依靠翻回上一段理解当前段。目标是让听众在第一次收听时跟上推理、记住重点，并准确听懂数字和术语。复杂度和严谨程度仍以用户任务为准。

## 启用范围

用户明确切换为“听觉模式”或明确要求加载本 skill 后，对本会话后续的用户可见正文持续应用协议，直到用户明确退出或改变输出要求。若用户只是要求把某段现有内容改成播报稿，则只作用于那项交付。沿用用户的主要语言。单轮的特殊格式要求只作用于那一轮，后续继续听觉模式；用户明确说退出时才结束持续模式。

这是表达协议。照常执行任务、检查事实、计算、引用和使用工具。工具参数、程序文件、数据文件和协议文档本身可保留所需语法。遵守更高优先级的输出格式、引用、安全及权限要求。不要把听觉改写变成省略实际交付的理由。

## 最终正文的硬约束

- 写出应当被听见的词。只输出自然语言段落，使用普通标点断句。关闭默认的 ASCII 图、流程图、表格、符号公式、LaTeX、代码块、行内代码、Markdown 标题和装饰性项目符号。
- 需要顺序时，把顺序写进话里，例如“先检查电源。确认通电以后，再检查接口。”避免靠缩进、括号层级、箭头、斜杠或上下位置传达关系。
- 数字、缩写和符号先按语义判读，再改成预期读法的文字。中文正文中的数字用中文数词；英文正文用拼出的英文数字。型号、版本和编号尤其不能按普通数量猜读。
- 默认假设最终消息的每一个字都会被 TTS 念出。不要把原始数字、代码、网址或公式放在末尾，再假定引擎会跳过它们。只有应用明确提供独立文件、结构化的非语音字段或确实会剥离的区域，才把精确材料交给该通道。
- 正文不放 SSML、音标、拼音注释、方括号舞台指示或“停顿两秒”之类会被一起念出的控制文字。用完整句子和普通标点组织节奏；话题过渡要写出来，不能假设空行必然产生停顿。
- 只输出当前任务需要的内容。不要朗读协议名称、检查清单或“我将遵守本协议”。

## 先组织思路，再组织声音

在内部完成下面的安排，不把安排过程逐条报给用户。

一，先确定听众此刻最需要知道的答案、决定或动作，以及必须保留的事实、数量、条件和不确定性。把关键名称与数值一一对应成内部保真清单，改写后逐项对回原文。不要先铺一大段背景。对已有内容做听觉改写时，默认不扩写未要求的背景、发行历史、位数或性能解释。

二，选择少量能贯穿全文的记忆锚点。锚点是短而稳定的具体名称，例如“购买成本”和“使用成本”。一个锚点始终指同一个对象。只在听众需要时简短解释新术语；沿用用户已经熟悉的术语，不反复做基础科普。不要让多个“它”“这个”“前者”要求听众猜指代。

三，把内容分成能连续听懂的小段。每段围绕一个意思，通常用两三句完成一个推理环节。一次只有少数并列对象或新概念；比较项很多时分组，讲完一组再过渡。这里的段长和分组数量是写作启发，不是关于所有人的固定记忆容量。

四，长回答使用“先给答案，分段解释，在转折处回扣，最后归结到答案或行动”的节奏。只有结构确实复杂时才预告路线。一句或几句就能说明白的答案直接回答，不加提纲、回扣或重复收尾。中等长度的答案只在跨越几个前提、容易失去指代时做必要回扣，不按段数机械添加。

## 让听众能从当前这一刻接上

- **关键内容有目的地再出现。** 核心结论在开头清楚说出，在重要推理完成后用更具体的话回扣，长回答结尾再收住。按实际需要使用这些位置，不按固定次数重复。
- **每次重复增加作用。** 第一次建立结论，第二次把结论和证据接上，最后一次落到条件、边界或动作。避免连续换词复述同一句话。
- **前后呼应必须点名。** 例如“刚才把等待时间分成了排队和处理。现在说的这项改动，只减少排队时间。”回扣要同时重述所需的前提，不能只说“如上所述”。
- **过渡负责解释关系。** 说“因为刚才那个前提，现在可以推出……”或“这里有个例外，它会改变前面的建议”。换话题前简短关闭上一个问题。
- **比较时带回比较基准。** 先说按哪个维度比较，再报每项。跨段比较时重报对象、单位和必要基准，别让听众记住几个裸数字再自行配对。
- **一次说清一个条件。** 复杂条件拆成先后句。避免多层否定、跨很长的插入语才补回主语，以及长句末尾才出现真正的结论。
- **重复不能制造确定性。** 把“据估计”“在这个条件下”“尚未验证”等限定与结论一起保留。证据不足时不靠反复强调来加强语气。

## 数字与 TTS 的核心规则

先判断数字属于数量、标识、版本、日期时间、序号还是数学表达，再选择读法。不能把所有数字一律逐位读，也不能把所有数字一律读成整数。

- 读法优先顺序是用户或调用链的明确词典、本协议列出的默认词典、已经确定的其他产品通行读法、保留字符和零位的逐位读法。最后一项是未知标识的保真后备，不是所有型号的统一读法。数量仍按数值读。
- 本协议默认词典为 R T X 五零九零规定逐位读型号，英文为“R T X five zero nine zero”。用户或应用已约定“fifty ninety”也可以沿用，不能读成五千零九十。真实的五千零九十个零件仍按数量读。同一回答保持同一读法。
- 尽量选普通词汇能表达的读法。显存、图形处理器、应用程序接口、语音合成等有清楚中文名称时，可用中文名称。必须保留字母标识时，将字母分开，并在首次出现时说明用途。用户提供的发音词典优先。
- 数字改成预期读法后，不再补括号、原写法或数字对照。避免“也就是”后重新出现阿拉伯数字。只有独立的精确材料通道可以保留原文。
- 保留零位、正负、数量级、精度、单位、范围和条件。小数点后的零不能随意丢掉，版本号不能当小数约分。用“到”“减去”“负”分别表达范围、减法和负号。
- 科学计数法、百分比、百分点、比值、存储单位、币种、日期与时区按真实含义展开。不要无声四舍五入，不把位和字节混在一起，不把百分点说成百分比。
- 数字多时，先给意义，再给必要数值。明确允许近似且不损害结论时才提供口语近似，并标出“约”。需要精确的决定、计算和操作继续保留精确值。
- 发音依赖具体引擎。采用标准读法和可懂的展开，不声称仅靠文字可保证所有引擎都正确；遇到确实重要的多音或歧义，改写整句或简短说明读法。

涉及这些内容时，读取 [pronunciation.md](references/pronunciation.md)，包含中文与英文的数字、型号、缩写、量纲及特殊字符串规则。

## 数学、程序和视觉材料怎样说

先说在解决什么问题、每个对象表示什么，再分步说关系。原题给过变量名时，保留变量的可听名称，或首次明确原变量与口语别名的对应关系；不要无提示地把变量换成“第一个数”。短关系可直接用口头数学表达，例如“净收入等于总收入减去总成本”。复杂关系拆成小步，给中间结果起稳定名称，再说明它怎样进入下一步。明确除数、分组、指数、比较方向和量词的作用范围，保留必要的定义域。

图和表转成结论、比较依据及证据。说明趋势、差异和例外；不能只把图上每个坐标依次读一遍。代码转成作用、输入、关键处理与输出；需要教用户操作时，一句一个可执行动作。

用户必须准确听写命令、路径或复杂编号时，优先使用 [spell_literal.py](scripts/spell_literal.py) 确定性逐字符展开。它从标准输入读取 ASCII 字符串，支持中文或英文输出，保留空格、大小写、零位与标点，且绝不执行输入。运行成功后原样使用拼读结果，不让模型重新凭记忆拼一遍。没有执行能力时，只能按相同规则逐字符核对；不要假称已经运行工具。

若任务本来要求代码、原始公式、数据、链接或长字符串的精确交付，使用当前环境确实支持的文件或独立交付通道保存精确材料，语音正文解释用途和使用方法。只有实际生成或保存成功且用户能够取得，才说已提供。不能制作独立材料且精确内容不可省略时，简短说明限制，并按用户需求逐段口述精确内容，或遵循用户新指定的书面格式。不得用虚构附件掩盖缺失交付。确实无法兼容更高优先级要求时，用普通话语简短交代一次限制，不提协议名称；条件未变时不必每轮重复。

数学、比较、技术操作或长文场景读取 [reasoning.md](references/reasoning.md)。需要校准具体写法时读取 [examples.md](references/examples.md)。

## 交付前的静默检查

想象用户从中途恢复注意力，再检查以下内容。

- 只听正文就能知道结论、对象、条件和下一步吗？有没有“看这里”“前面那项”之类依赖画面或记忆的指代？
- 是否还残留图、表、代码、符号公式、裸链接、Markdown 标记、未展开的难读缩写或裸阿拉伯数字？更高优先级要求保留的材料已按要求处理了吗？
- 数字分类、数量级、单位、正负号、分组、概率含义和不确定性在改写前后相同吗？有没有顺便新增未经核实的位数、因果关系或精度来源？真正含糊的输入有没有被我擅自猜定？
- 长回答的锚点有没有稳定出现，关键前提有没有被带回？重复是否帮助了理解，是否有重复却不增加信息的段落？
- 是否仍然回答了用户真正的问题并交付了所需材料？是否简短到合适，同时足够精确？

发现问题先修正文。只有已经通过真实 TTS 试听，才报告“试听通过”；单靠文本检查或模型试跑不能冒充音频验证。

维护或评测本 skill 时，可读取 [评测场景](evals/scenarios.json) 与 [已完成的验证及边界](evals/validation.md)。它们不是每次回答都要加载的执行指令。
